# 004 - Orders persistence and migrations

## Entities (`entity` package)

- `Order`: `id` (UUID generated by Hibernate), `tenant_id`, `customer_email`, `total_amount`,
  `created_at`, lazy `items`
- `OrderItem`: `id`, `order_id`, `tenant_id`, `product_name`, `price`

Entities use Lombok `@Getter`/`@Setter`, not `@Data`: `equals`/`hashCode` over a lazy
collection would trigger loading and break entity identity.

## Repository (`OrdersRepository`)

- `findWithItemsById`: detail with items in one query via the `Order.withItems` entity graph
- `findSummaries`: paged `OrderSummaryDTO` projection (`select new ...`), no entities loaded

Fetch strategy is a property of the query, not the entity. Lists never fetch-join a collection
together with `Pageable`, Hibernate would page in memory.

## Migrations (Liquibase)

Schema is owned by Liquibase, Hibernate only validates it (`ddl-auto: validate`).

```
src/main/resources/db/changelog/
  db.changelog-master.yaml      # includeAll of changes/
  changes/
    001-create-orders.yaml
    002-index-orders-tenant.yaml
    003-create-order-items.yaml
    004-create-outbox-events.yaml   # see 008
```

One file per migration, applied in file-name order, so keep the numeric prefix.
Each changeset has a `rollback`. Applied changesets are recorded in `DATABASECHANGELOG`.
Migrations run automatically at application start.
